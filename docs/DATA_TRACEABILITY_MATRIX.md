# SocratiQ V2 — Event-to-Database Traceability Matrix

## Executive Summary
This document provides a comprehensive end-to-end audit of all 12 data pathways in SocratiQ V2, verifying event origination, backend handling, validation gates, database persistence, student/session identification, deduplication, fault tolerance, and teacher dashboard consumption.

Importantly, this audit confirms that **operational telemetry is never treated as educational evidence**, and cross-student data boundaries are strictly enforced via RLS and server-side tenancy scoping.

## Detailed Audit Findings

### 1. Telemetry vs. Educational Evidence Separation
- **Finding:** Operational telemetry (such as `StageTimer`, stage durations, first-text timestamps, and internal latency benchmarks) is tracked strictly in-memory or in application log streams (`backend/app/streaming.py`).
- **Verification:** Telemetry is **never** written to `learning_events` or `evidence_candidates`. The `learning_events` table contains only genuine student pedagogical events (`STUDENT_MESSAGE`, `COACH_RESPONSE`, `BOARD_DRAW`, `PERSONA_CHANGED`, `VERIFICATION_SUBMISSION`).

### 2. Multi-Tenancy and Cross-Student Isolation
- All tables in Supabase have Row Level Security (RLS) enabled.
- `student_preferences` enforces `student_id = app.current_user_id()`. Verified with live cross-student test: Student S1 querying the database receives 0 rows when attempting to select Student S2's preferences.
- All teacher queries join on `enrollments e WHERE e.course_id = ... AND e.status = 'active'`, preventing cross-course or cross-university leakage.

### 3. Attempt and Assignment ID Linkage
- Coach interactions, whiteboard snapshots, and verification runs enforce valid foreign keys to `attempts(attempt_id)` and `assignments(assignment_id)`.
- Replaying a turn from another student or another assignment is rejected with HTTP 404/403.

### 4. Idempotency and Duplication Prevention
- Chat turns support `client_turn_id` in payload. Retrying a dropped HTTP connection replays the already-saved response without generating a duplicate `ai_interactions` row or re-invoking the LLM.
- Persona selection uses `ON CONFLICT (student_id) DO UPDATE`, guaranteeing exactly one preference row per student.
